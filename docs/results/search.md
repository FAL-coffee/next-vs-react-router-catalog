# 検索操作の応答（localhost、Playwright + Chromium、2026-10-05）

一覧画面で検索語を入れて「検索」を押してから、結果の商品カードが描画されるまでの時間。
検索語は毎回変えて 6 回測り、最初の 1 回と中央値を記録（同じ検索語を繰り返すと TanStack Router の loader キャッシュが効いて SPA が 50 ms 前後になるため）。
両方ともモックデータ層の 150 ms を含む。制限環境は Chrome DevTools Protocol で下り 1.6 Mbps・追加レイテンシ 150 ms・CPU 4 倍スローダウン。

| | Next.js（既定: 素の `<form method="get">`） | Next.js（`next/form` に差し替え） | TanStack Router SPA |
| --- | ---: | ---: | ---: |
| 通常：初回 / 中央値 | 317 / 291 ms | 255 / 219 ms | 203 / 204 ms |
| 制限環境：初回 / 中央値 | 534 / 496 ms | 329 / 298 ms | 302 / 234 ms |
| 検索ごとのページ全体の再読込 | あり（6 回中 6 回） | なし | なし |

所見:

- create-next-app の既定どおり素の `<form method="get">` を使うと、検索のたびにページ全体が再読込される（SSR + JS 再実行）
- `next/form` に替えるとソフトナビゲーションになり RSC payload だけ取りに行くので、制限環境で 500 ms → 300 ms まで縮む。「とりあえず既定」と「知っていれば直せる」の差
- SPA はブラウザ内で loader を回すだけで通信がなく、制限環境でもほぼ変わらない
- 実運用では SPA の検索は BFF への往復（ネットワーク RTT + API）になるので、この差はそのぶん縮む。Next.js はサーバから API を呼ぶぶん往復が短い
